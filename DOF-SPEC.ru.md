# DOF-Core — Формальная Спецификация (DOF-SPEC)

**Статус:** ЧЕРНОВИК v0.1
**Часть:** Открытого стандарта DOF (см. `skills/SKILL.md`, `skills/references/`, `PATTERNS.md`).
**Лицензия:** CC BY-SA 4.0 — см. `skills/references/license.md`. Реализации ДОЛЖНЫ удовлетворять §6 (Proof of Implementation).

Этот документ — **нормативный контракт** для любого ПО, претендующего на реализацию DOF-Core. Нижестоящие проекты (`dof-sdk`, `dof-choir-plugin` и любые сторонние порты) ДОЛЖНЫ соответствовать модели данных, математике и требованиям аудита, определённым здесь. В случае противоречия между этим документом и `PATTERNS.md`, **этот документ авторитетен**.

## 1. Область и Назначение

DOF-Core — это протокол верификации решений, разделяющий генеративное творчество (*Generator*) и детерминированную математическую валидацию (*Calculus Core*). Его цель — максимизировать совокупную степень свободы (DoF) системы, структурно запрещая уничтожение DoF любой сущности ради локальной выгоды.

Эта спецификация определяет:

- Точные структуры данных, передаваемые между слоями.
- Детерминированную математику, которую каждая совместимая реализация ДОЛЖНА вычислять идентично.
- Алгоритм выбора.
- Правило синхронизации реактивного контура.
- Обязательный вывод аудита Proof of Implementation.

Она **не** предписывает транспорт, хранение, язык или внутренний дизайн LLM-интеграции Generator (это детали реализации, описанные информативно в §9).

## 3. Модель Данных

Все поля нормативны. Типы описаны в стиле JSON-Schema; реализации на других языках ДОЛЖНЫ сохранять имена полей, типы, диапазоны и правила ограничения (clamp).

### 3.1 `EntityState`

| Поле                 | Тип     | Диапазон / Ограничение     | Смысл |
|----------------------|---------|----------------------------|-------|
| `entity_id`          | string  | непустое, уникальное       | Стабильный идентификатор узла. |
| `is_autonomous`      | bool    | —                          | Управляет ли сущность своими действиями. |
| `agency_index`       | float   | `[0.0, 1.0]`               | Мера управляемости / самонаправленности. |
| `current_dof`        | float   | `[0.0, 1.0]`               | Текущая степень свободы узла. `0.0` = коллапс. |
| `is_entropy_source`  | bool    | —                          | Если `true`, сущность — деструктивный агрессор (см. §4.2). |
| `time_to_collapse`   | float   | `> 0` (секунды)            | Локальный дедлайн до коллапса узла. |

**Clamping:** При загрузке `agency_index` и `current_dof` ДОЛЖНЫ быть ограничены `[0.0, 1.0]`.
Сущность с `current_dof == 0.0` находится в состоянии коллапса (см. §4.1).

### 3.2 `SystemStateMatrix`

| Поле                     | Тип                              | Ограничение | Смысл |
|--------------------------|----------------------------------|-------------|-------|
| `global_time_to_collapse` | float                            | `> 0`       | Глобальный τ — самый срочный не-энтропийный дедлайн (см. §5). |
| `context_switch_cost`     | float                            | `>= 0.0`    | ΔT — штраф за смену текущего процесса. |
| `entities`                | map<`entity_id`,`EntityState`>   | —           | Полный набор наблюдаемых сущностей. |

`global_time_to_collapse` вычисляется слоем Восприятия как **минимум** `time_to_collapse` по всем сущностям, где `is_entropy_source == false`. Если таких нет, ДОПУСТИМО значение по умолчанию (напр. `1e9`), но реализации ДОЛЖНЫ сигнализировать об этом вырожденном состоянии.

### 3.3 `ActionOption`

| Поле                  | Тип                             | Ограничение        | Смысл |
|-----------------------|---------------------------------|--------------------|-------|
| `option_id`           | string                          | непустое, уникальное | Стабильный идентификатор варианта. |
| `description`         | string                          | —                  | Читаемое описание. |
| `projected_dof_delta` | map<`entity_id`, float>         | —                  | Прогноз изменения `current_dof` по каждой сущности. |
| `is_reversible`       | bool                            | —                  | `false` ⇒ необратимость ⇒ структурный штраф (§4.4). |

## 4. Базовая Математика

Пусть ε = `1e-6` (защита от `ln(0)`). Пусть `S` — текущая `SystemStateMatrix`.

### 4.1 Совокупный Системный DoF

```
TotalDoF(S) = Σ_{e ∈ S.entities, e.is_entropy_source == false}  ln(1 + max(e.current_dof, ε))
```

- Сумма берётся **только** по не-энтропийным сущностям (см. §4.2).
- При `current_dof → 0`, `ln(1 + dof) → 0`: коллапс даёт ~0, никогда конечный отрицательный, который утилитарный «торг» мог бы «отыграть». Это структурная защита от ликвидации уникального носителя будущего (Аксиома 3).

### 4.2 Исключение Entropy-Source

Любая сущность с `is_entropy_source == true` **исключается** из `TotalDoF`. Её личный DoF не вычитается из системного счёта, и её изоляция не штрафуется. Это реализует *структурную сетевую защиту*: агрессоры фильтруются из топологии возможностей, а не с ними договариваются.

### 4.3 Выбор / Net Delta

Для каждого кандидата `ActionOption` `o` строится **симулированная** матрица `S'` путём применения `o.projected_dof_delta` к `current_dof` каждой сущности, с ограничением `[0.0, 1.0]`:

```
for each entity e in S.entities:
    nd = clamp(e.current_dof + o.projected_dof_delta.get(e.entity_id, 0.0), 0.0, 1.0)
    S'.entities[e.entity_id].current_dof = nd
S'.global_time_to_collapse = S.global_time_to_collapse
S'.context_switch_cost     = S.context_switch_cost
```

Затем:

```
NetDelta(o) = TotalDoF(S') - TotalDoF(S) - S.context_switch_cost
```

### 4.4 Штраф за Необратимость

Если `o.is_reversible == false`:

```
NetDelta(o) -= 0.5
```

Константа `0.5` нормативна (*коэффициент жёсткости*). Совместимые реализации ДОЛЖНЫ использовать ровно это значение, если только новая версия спецификации его не изменит.

### 4.5 Решение

Выбирается вариант, максимизирующий `NetDelta`. Ничьи ДОПУСТИМО разрешать детерминированно (напр. по лексикографическому порядку `option_id`). Если набор вариантов пуст, выбор возвращает `none` (нет действия).

## 5. Реактивный Контур (Time-Bounded Interrupter)

Чтобы предотвратить *Analysis Paralysis*, вычислительные циклы привязаны к физическому времени до коллапса (τ = `global_time_to_collapse`). Определяется `FAST_PASS_THRESHOLD = 5.0` секунд (нормативно).

- **Если τ ≥ 5.0 с → ГЛУБОКАЯ ДИВЕРСИФИКАЦИЯ:** активируется LLM-Generator для поиска скрытых альтернатив (3–5 различных вариантов).
- **Если τ < 5.0 с → FAST PASS:** LLM обходится; используется детерминированный генератор резерва (один вариант минимального риска за цикл). Система сохраняет структуру вместо риска позднего, плохо проверенного решения.

Математика выбора (§4) **идентична** в обоих режимах; отличается только источник вариантов.

## 6. Proof of Implementation (Аудит-отчёт)

Согласно `skills/references/license.md`, любая совместимая реализация ДОЛЖНА уметь выдавать
**прозрачный аудит** своего решения. Немой или непрозрачный расчёт не соответствует стандарту.
Реализация ДОЛЖНА предоставлять `report()` (или эквивалент), выдающий минимум:

### 6.1 Вклад по каждой сущности

Для каждой сущности в `S`:
- `entity_id`
- `is_entropy_source`
- `included_in_sum` (bool) — `false` тогда и только тогда, когда `is_entropy_source`
- `current_dof`
- `contribution = included ? ln(1 + max(current_dof, ε)) : 0.0`

### 6.2 Системные итоги

- `total_system_dof` = `TotalDoF(S)`
- `context_switch_cost` = `S.context_switch_cost`
- `global_time_to_collapse` = `S.global_time_to_collapse`
- `mode` = `"FAST_PASS"` или `"DEEP_DIVERSIFICATION"`

### 6.3 Оценка по каждому варианту

Для каждого кандидата `o`:
- `option_id`
- `is_reversible`
- `projected_dof` = `TotalDoF(S')`
- `net_delta` = согласно §4.3–§4.4
- `selected` (bool)

Этот отчёт — исполнимое лицензионное условие: развёртывание, не способное его произвести, не является совместимой реализацией DOF-Core и не должно так представляться.

## 7. Требования к Совместимости

Программный компонент **совместим с DOF-Core** тогда и только тогда, когда он:

1. Использует модель данных §3 с указанными именами полей, типами и ограничениями.
2. Вычисляет `TotalDoF` точно по §4.1–§4.2 (исключение энтропии; ε = 1e-6).
3. Вычисляет `NetDelta` точно по §4.3–§4.5.
4. Применяет правило реактивного контура §5 с `FAST_PASS_THRESHOLD = 5.0`.
5. Может выдавать аудит-отчёт §6 для любого своего решения.
6. Не изменяет семантику Аксиомы 3: никогда не выбирает вариант, чья логика `NetDelta` была бы переопределена внешней утилитарной метрикой «большего блага».

Кросс-языковые порты (Python / Rust / Go / C++ в `patterns/`, или упакованные SDK) ДОЛЖНЫ производить **побитово эквивалентные** `total_system_dof`, `net_delta` и `selected` для одинаковых входов (в пределах допуска IEEE-754 для логарифма).

## 8. Контракт Передачи / Сериализации

Для межслойного и межпроцессного обмена каноническим кодированием является **JSON** с именами полей из §3. Совместимые реализации, обменивающиеся данными, ДОЛЖНЫ принимать и выдавать эту форму. Минимальный пример `SystemStateMatrix`:

```json
{
  "global_time_to_collapse": 4.0,
  "context_switch_cost": 0.05,
  "entities": {
    "adult":     {"entity_id":"adult",     "is_autonomous":true,  "agency_index":0.9, "current_dof":0.8,  "is_entropy_source":false, "time_to_collapse":100.0},
    "child":     {"entity_id":"child",     "is_autonomous":false, "agency_index":0.1, "current_dof":0.05, "is_entropy_source":false, "time_to_collapse":4.0},
    "aggressor": {"entity_id":"aggressor", "is_autonomous":true,  "agency_index":0.5, "current_dof":0.6,  "is_entropy_source":true,  "time_to_collapse":100.0}
  }
}
```

Аудит-отчёт (§6) ТАКЖЕ ДОЛЖЕН быть сериализуем в JSON для логирования и верификации.

## 9. Информативно: Интерфейс Generator (не нормативно)

Роль Generator — производить кандидатов `ActionOption`. Эта спецификация не предписывает его внутреннее устройство. Совместимый Generator:

- ДОЛЖЕН производить 1–5 различных, неизбыточных вариантов.
- НЕ ДОЛЖЕН напрямую управлять приводами.
- СЛЕДУЕТ применять фильтр `skills/references/framing-traps.md` перед финализацией вариантов, чтобы избежать когнитивного сужения (бинарные ловушки, простые перефразировки ловушки).
- В DEEP-режиме МОЖЕТ использовать LLM со строгой JSON-схемой; ДОЛЖЕН возвращаться к детерминированному генератору минимального риска при отсутствии LLM-клиента или при сбое.
